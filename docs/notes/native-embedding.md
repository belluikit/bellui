### Native View Embedding — widget.NativeViewHost + webview (#45, spike)
`widget.NativeViewHost` embeds an OS-owned view (web view, native video, map, camera preview) at a widget's position. It is a **hole punch**, the architecture Flutter/Compose Multiplatform/Avalonia ship: bellui draws its scene into one GPU surface and an OS view cannot be composited into it, so the host **draws nothing** and drives a real platform view positioned over the canvas. The spike (#45) decided **(A) hole punch over (B) offscreen-render-to-texture** — (B) is impossible on macOS/iOS (WKWebView has no supported offscreen API) and would mean bundling CEF (~150–200 MB) on every platform, untenable for a toolkit with a 385 KB font budget (#686).
- **Limitations are properties of the approach, stated in the widget doc comment and measured, not assumed**: nothing bellui draws appears above it (every `PopUp`, dialog, menu, `Tooltip`, `Toast`, `Snackbar`, `CompletionPopup`, selection handle/loupe is occluded); `Canvas.Capture` sees a hole (so golden tests, the #473 pre-capture repaint path and the `hack/*probe -auto` convention capture what bellui drew *underneath*); `RepaintBoundary` FBO caching, dirty-region culling, `SetGroupOpacity`, world transforms and `DirectionScope` mirroring do not reach it; clipping must be reimplemented per platform as a native clip/mask.
- **Backend contract** — `widget.NativeView`: `Attach(win bellui.Window) error` (reaches the native handle via `driver.NativeWindow.RunNative`), `SetGeometry(rect, clip geo.Rectangle, scale float32)` (canvas-absolute bellui points; `clip` is the region to mask to), `SetVisible(bool)`, `Destroy()` (idempotent). A failed `Attach` leaves the host **inert** — it occupies its space and draws nothing — never a panic, so a cross-platform app compiles and degrades everywhere.
- **Zero core changes.** The geometry story rides three seams that already existed: `driver.AncestorsOfObject` (visible-tree membership — a false `ok` covers hidden/hidden-ancestor/removed in one test), `bellui.Driver.AbsolutePositionForObject` and `driver.ClipBoundsForObject`. That cheapness is the main argument for (A).
- **Per-frame ticker** (the #417 prefill / #758 selection-handle pattern): a native view is not in the widget tree so no layout pass reaches it — only re-evaluating every frame keeps it glued to a host a parent scroll/resize/animation is moving. **Cost is negligible**: ~765 ns at nesting depth 1, ~1.1 µs at depth 8 (0.007% of a 16.6 ms frame), 6.9 µs at depth 128 (`BenchmarkNativeViewHostSyncDepth`); an unchanged host never reaches the platform (probe: 772 evaluations → 5 backend calls). **Ticker lifetime ≠ visibility**: it stops only when the host leaves the visible tree or loses its canvas (states a widget-level event re-enters), and deliberately keeps running while the host is merely scrolled out of a clipping ancestor — nothing else would notice it scrolling back. Follow-up #61 collapses the three tree walks into one.
- **`webview` package** — optional import (the `theme/cjk` placement pattern), so the platform web engine is only linked by binaries that import it. macOS `WKWebView` backend (`webview_darwin.{go,m,h}`, MRC like every other ObjC bridge here); targets without a backend — the BSDs, and Linux built with CGO_ENABLED=0 — compile `webview_unsupported.go` with `Supported == false`, a contract locked by `webview_unsupported_test.go`. Callbacks cross cgo by **token, not Go pointer** (mutex-guarded registry) and arrive on the main thread where the bellui main goroutine sits, the a11y-AXPress callback model. **The hole punch constrains compositing and input focus, not data flow.**
- **Bridge + navigation API (#66)** — the spike's two bare primitives (`Eval(js)`, `OnMessage func(string)`) were replaced by a designed, **portable** API, settled here once so #62/#63/#64/#65 don't each grow their own shape. The package is now split **portable / platform**: `bridge.go`, `eval.go`, `navigation.go`, `webview.go` are shared, and `platform.go` is the one-page seam contract a backend implements (`attachRaw`/`destroyRaw`/`attachedRaw`/`evalRaw`/`evalResultRaw`/`loadURLRaw`/`loadHTMLRaw`/`navRaw`, calling in through `deliverMessage`/`deliverEvalResult`/`deliverLoad`/`decideNavigation`). Everything is main-goroutine, in both directions.
  - **The bridge is opt-in, and origin-gated.** `EnableBridge(OriginPolicy)` before `Attach` is what installs it, and with it off the backend adds **no script message handler and no user script at all** — the page has no `window.bellui`, not an ignored one (probe-measured: `typeof window.bellui` is `"undefined"` on a view without it). `OriginPolicy` (`TrustAllOrigins`, `TrustOrigins(…)`, nil = trust nothing) is consulted on **every** inbound message including sub-frames, against a serialized origin (`https://host[:port]`, `file://`, or `OriginOpaque` = `"null"` for data:/about:blank/sandboxed). This is the `RichText.AllowRemoteContent` (#285) stance applied to a message channel: a channel installed for a trusted local page is the one a remote page inherits when the user follows a link.
  - **One envelope, standardised once** (`{v,kind,id,name,payload,error}`, kinds `post`/`call`/`reply`), spoken in both directions on every platform, so an app never invents its own id scheme. Page side is the shared `bridgeShim` JS const with a `/*POST*/` placeholder each backend fills with its own transport (WKScriptMessageHandler / `@JavascriptInterface` / `postMessage` / `WebMessageReceived`), injected at document start so it survives navigation. It gives the page `bellui.post`, `bellui.call(name,arg) → Promise`, `bellui.handle(name,fn)` and `bellui.onMessage`; Go gets `OnMessage`, `Handle(name, Handler)`, `Post(payload)`, `Call(name, arg, cb)`. Payloads are JSON both ways (`Message.Decode`).
  - **Injection safety**: `Call` passes arguments as data. For pages that can't cooperate, `EvalFunc(body, Args{…})`/`EvalFuncResult` wrap the body in an IIFE whose **parameters** carry the JSON-encoded values (names validated as JS identifiers, sorted for determinism), so nothing from outside becomes source. Raw `Eval` is kept, with the footgun documented.
  - **Eval results**: `EvalResult(js, cb)`/`EvalFuncResult` deliver the script's value as JSON or an error — the discarded `evaluateJavaScript:` completion handler #66 opened on. On darwin the useful message is `userInfo[WKJavaScriptExceptionMessage]`, **not** `localizedDescription` (which is always the useless "A JavaScript exception occurred").
  - **Lifecycle is a decision, not an accident**: every callback this package accepts is invoked **exactly once**. Unattached/destroyed → `ErrNotAttached`; bridge off → `ErrBridgeDisabled`; `Destroy` fails all pending calls (handlers survive, so a view can be re-attached); a `Call` is sent *as an eval with a result* so a page with no shim fails it immediately instead of waiting for a reply that cannot come; a page `call` naming an unregistered handler **rejects** the page's promise rather than hanging it. Only a page handler that never settles its own promise stays pending (documented as the page's responsibility).
  - **Navigation**: `LoadURL`/`LoadHTML`/`Reload`/`StopLoading`/`GoBack`/`GoForward`/`CanGoBack`/`CanGoForward`, `LoadState()` + `OnLoadChanged(LoadEvent{State,URL,Err})`, and the veto hook `OnNavigate(NavigationRequest{URL,Kind,MainFrame,NewWindow}) bool`. A refusal (and `StopLoading`) reports `LoadStateFailed` with `ErrNavigationCancelled` — matchable with `errors.Is` because bellui's own cancellations go through `reportLoad(err error)` rather than the backend's string seam. **`URL()` never follows a failed or refused navigation** (fixed after the probe caught it reporting the blocked URL). `NewWindow` is a `target=_blank`/`window.open` action: there is no second window, so an allowed one loads in place. **Platform property, not papered over**: WebKit builds no back-forward entry for `loadHTMLString` with no base URL, so `CanGoBack` can be false after `LoadHTML`.
  - **Verify**: `hack/webviewprobe -auto` grew `[NAV]` and `[TRUST]` blocks and a much wider `[BRIDGE]` one; all confirmed on a real WKWebView. The trust and history measurements navigate to a **local HTTP server** the probe starts (`serveProbePages`) — a genuinely different origin and a real session history, still with no network. Portable unit tests (`bridge_test.go`, `navigation_test.go`) drive the whole bridge through a fake engine installed on the `evalHook` seam, so they run on **every** CI leg, not just macOS. Fixed alongside: the darwin build linked `CALayer` only by accident of another package's frameworks — `-framework QuartzCore` is now explicit (found by building the package's own test binary for the first time).
- **macOS shape**: a *flipped*, layer-backed clip `NSView` with `masksToBounds` (carrying the clip rect, which is what makes `container.Scroll` clipping work) added as a **subview of the GLFW content view**, with the `WKWebView` inside it; flipping means the inner frame needs no second coordinate conversion. **The #1124 iOS lesson does not transfer** — a subview of the content view composites cleanly on AppKit, no CAMetalLayer entanglement (iOS must still host as a *sibling* of the GLKView, #64). The cgo boundary passes the NSWindow as `uintptr_t` (the `dialog/file_darwin_native.go` precedent), avoiding `go vet`'s `unsafe.Pointer` warning.
- **Windows backend — WebView2 through hand-rolled Go COM (#65)**. The repo's cgo-free Windows convention (`dialog/file_windows_native.go`) proves COM *calling* through `x/sys/windows` syscalls; WebView2 is callback-driven, so this backend also *implements* COM — a Go struct whose first word points at a vtable of `syscall.NewCallback` addresses. **All eleven handler kinds share one vtable**: `Invoke` has the same arity `(this, a, b)` in every WebView2 handler interface, so the kind stored in the object distinguishes a finished eval from an arriving message and the process spends four callback slots in total. Handlers are resolved **through a registry keyed by address**, not by casting `this` back to a Go pointer — the same map both keeps the Go object out of the collector while the engine holds a reference (refcounted; it leaves on the last `Release`) and makes a stale callback resolve to nothing instead of into reused memory. Vtable slot numbers and IIDs are ABI facts from `WebView2.h`, cross-checked against two independent bindings; `put_Bounds` is the one call whose **shape depends on the architecture** (a 16-byte `RECT` by value: x64 passes its address, ARM64 packs it into two registers, 32-bit pushes four words) and so lives in `webview2bounds_windows_{amd64,arm64,other}.go`.
  - **No redistributable, no embedded blob.** `WebView2Loader.dll` is used when the app ships one; otherwise the backend does what that DLL does — reads the Evergreen Runtime path from `HKLM/HKCU\SOFTWARE\Microsoft\EdgeUpdate\ClientState\{F3017226-...}` (32-bit view), checks the API version in the path is >= 1150, and calls `CreateWebViewEnvironmentWithOptionsInternal` in `EBWebView\<arch>\EmbeddedBrowserWebView.dll`. `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER` selects a fixed-version runtime, `WEBVIEW2_USER_DATA_FOLDER` the profile (default `%LOCALAPPDATA%\<exe>\WebView2` — the runtime's own default sits beside the executable, which is not writable under Program Files). **No runtime present -> `Attach` reports `webview.ErrRuntimeMissing`** (declared portably so `errors.Is` needs no build tag) and the host is inert, the documented degradation.
  - **Attach is asynchronous**, because environment and controller creation both complete on the message loop. `Attach` returns as soon as the request is accepted and everything asked of the view meanwhile is **queued and replayed in order** when the controller arrives; pumping messages to make it synchronous would re-enter the driver's window procedure from inside a widget lifecycle call, the #973 deadlock shape. Callbacks arrive on the main goroutine (re-entered while the driver pumps), so they are delivered directly, as on darwin.
  - **Native clip is a child HWND.** WebView2 has only `Bounds`, and shrinking it re-lays-out the page rather than revealing less of it, so the controller is parented to a `BelluiWebViewClip` child window sized to the clip with the web view offset inside it — the macOS clip view expressed in HWNDs. `WS_CLIPCHILDREN` is set on the glfw window so its GPU painting cannot flash over the hole. **Focus**: `TakeFocus` is `MoveFocus(PROGRAMMATIC)`, `ResignFocus` is `SetFocus(<glfw HWND>)` (the window the driver installs its key handling on — the direct analogue of the macOS content-view rule), and `HasFocus` is a **shadow** fed by the controller's `GotFocus`/`LostFocus` (WebView2 has no getter, and the host polls it every frame). **Origin** comes from the engine's document URI reduced by the portable `serializeOrigin` (`webview/origin.go`, tested on every CI leg) — an allowlist of http/https/file, everything else opaque — never from the message. With the bridge off, `IsWebMessageEnabled` is switched off outright, so `window.chrome.webview.postMessage` is not merely ignored but absent.

- **Focus bridge (#59)** — keyboard focus lives in the platform responder chain, which `Canvas.Focus` knows nothing about, so focus used to **split silently** (keystrokes and IME to the engine, bellui still drawing a focused, blinking `Entry`). `widget.NativeViewFocuser` is the optional backend capability that closes it: `TakeFocus`/`ResignFocus`/`HasFocus` (implemented by `webview.WebView`; `ResignFocus` on macOS makes the **GLFW content view** first responder specifically — making the *window* the responder would route keys to nothing, since GLFW installs its key handling on the content view). The host bridges both directions on the **same per-frame sync as the geometry**, by polling `HasFocus` rather than making every platform grow a focus-change notification: a native gain calls `Canvas.Unfocus()`, and — keyed on the invariant that a native gain *always* clears the canvas focus — "native holds the OS focus **and** bellui has a focused widget" can only mean bellui took it since the last frame, so the host calls `ResignFocus`. Hiding, scrolling fully out and teardown also resign (a hidden view holding the keyboard would swallow keystrokes with nothing on screen). Programmatic entry is `NativeViewHost.FocusNativeView()`, state is `NativeViewFocused()`; a backend without the capability keeps the old behaviour and bellui's focus is untouched. The poll costs nothing measurable on the Go side (1046 ns vs 1078 ns at nesting depth 8, `BenchmarkNativeViewHostSyncFocus`). **Tab-order decision: a `NativeViewHost` is deliberately NOT a Tab stop** (it does not implement `event.Focusable`) — once the platform view holds the OS focus bellui never sees the Tab key and so could not move focus back out, which would be a **keyboard trap (WCAG 2.1.2)**, worse than not being Tab-reachable; locked by `TestNativeViewHost_NotATabStop`. Verified on a real WKWebView: `hack/webviewprobe -auto`'s `[FOCUS]` block reports CONFIRMED in both directions.
- **Linux: WPE is rejected (#60); CEF was adopted (#105) through that block's own recorded trigger.** The policy that made every other platform cheap: **each backend uses the platform's own engine, so no web engine is bundled into a bellui binary** and CVE duty stays with the OS vendor. Linux is the only target with no engine usable that way, and #60 originally concluded it should therefore have no backend at all — a conclusion since reversed on its own terms (a concrete consumer appeared and accepted CEF's costs deliberately; see the next block for what shipped and what it costs). The WPE rejection itself stands unchanged, and its reasoning is what selected CEF. An out-of-tree engine also remains possible for an app that wants a different one — `widget.NativeView` is public with no unexported methods, so a backend can be implemented **out-of-tree** and hosted with `widget.NewNativeViewHost`, unchanged; whoever supplies it pins their own engine version and ships it in their own Flatpak/AppImage, while bellui takes on neither the size nor the CVE rebuilds. (It must supply a native clip in `SetGeometry` or it overflows an enclosing `Scroll`, and `NativeViewFocuser` or focus drifts.) **"Just require users to install CEF" does not work**: no mainstream distro packages CEF (Debian/Ubuntu/Fedora none; Arch AUR-only source build), and CEF has no stable ABI — upstream expects apps to bundle the exact build they compiled against, which is why every Electron app carries its own Chromium. On availability CEF is *worse* than WPE. Windows differs only because WebView2 is a genuine system component (near-universal, OS-managed, ABI-stable). The spike was run on real hardware and settled the technical questions: architecture (B) *works* (WPE frames composited **inside** bellui's canvas at 94.6% of the surface, with bellui drawing over them — genuinely better than the hole punch), WPE renders offscreen headless, and the GPU vendor is irrelevant (`WPEDisplayHeadless` exposes no DRM device, so it is SHM by construction on any hardware). It was rejected anyway, on **operational risk, not size**: 112 unbundled shared-library dependencies whose ABI we do not control (ICU bumps soname every major — `libicuuc.so.78`; `libxml2.so.16`; libsoup-3.0; GStreamer); **absent from Ubuntu since 22.04**, and shipped by Debian *without* `ENABLE_WPE_PLATFORM` so the current API is missing there too (only Arch has both); zero-copy conditional on the user running **Wayland** (the DRM backend needs exclusive display control, the Wayland one needs `linux-dmabuf` negotiation) so X11 users get a silent CPU-copy fallback at 17–59% of a frame budget at 1080p — the same invisible-degradation shape that ruled out X11-only reparenting in #542; and a version-fragile integration (libwpe core-dumps without `WPE_BACKEND_LIBRARY`; newer WebKit paints nothing without an activity-state call absent in 2.36; the legacy export path silently stopped producing frames on 2.48/2.52 while remaining undeprecated). Packaging it ourselves would mean bundling those dependencies — converging on CEF's footprint, inheriting the arch × glibc-baseline matrix, still LGPL, still Linux-only, and ours to rebuild on every WebKit CVE. **The CEF-rejected-on-size reasoning in #45 is also corrected**: `libWPEWebKit-2.0.so` is **128 MB**, the same order as the ~150–250 MB that rejected CEF, and the figures are not like-for-like (WPE's excludes its dependency closure; CEF's is nearly self-contained). The real axis is *self-contained-and-portable* (CEF) versus *unbundled-and-distro-coupled* (WPE) — one design decision seen from two sides. **If desktop web embedding is ever pursued, CEF is the candidate to evaluate, not WPE** (BSD-3, prebuilt upstream, no distro-availability problem, no session-dependent performance cliff); its size and CVE-treadmill cost would have to be accepted deliberately — **which is exactly what happened**: that trigger fired in 2026-07 with a concrete consumer, and #60's phases delivered the backend below. None of this constrains `NativeViewHost` — a Linux backend for native video, a map or a camera preview carries no WebKit licence and stays possible. **The decisive signal, in one line: desktop distros are dropping it, and that is someone else's judgement made with better data than ours** — a distro removes a package when nothing depends on it and the burden (for a browser engine: an LTS-long CVE stream) is not justified. State it precisely though: upstream WPE is *healthy* (2.52.5 current, active development); what is missing is a **desktop constituency**. WPE's real users are embedded vendors (RDK, set-top boxes) who build from source in a BSP with a pinned version and toolchain — they never consumed distro packages, which is why Ubuntu dropped it and Debian kept a build without the current API. That makes it a **structural** mismatch, not a temporal one (waiting changes nothing), and it explains every integration trap the spike hit — version churn is absorbed by a BSP, so it is not a bug to WPE's actual users. Adopting it would put bellui *outside the library's intended consumption model*: building and redistributing it ourselves like a set-top-box vendor, but without the pinned hardware and version that make that tractable. A new WPE data point does not answer this; only a concrete consumer justifying a CEF evaluation would. Harness + evidence: `hack/wpeprobe` (`-tags wpe`).
- **Linux backend: CEF offscreen, composited into the canvas (#105).** The one backend that is **not** a hole punch — Wayland has no cross-toolkit embedding primitive and runtime X11/Wayland selection (#542) made an X11-reparenting view unshippable — so CEF renders offscreen (`windowless_rendering_enabled`) and hands BGRA frames to a streaming `canvas.Raster`. That dissolves the hole punch's whole limitation list: overlays/dialogs/menus draw above the content, `Canvas.Capture` sees it (golden tests and `-auto` probes assert on pixels), `RepaintBoundary`, clipping, group opacity and `DirectionScope` apply — and the host **is a Tab stop** (`event.Focusable`), the opposite of `NativeViewHost`, because bellui owns the keyboard and there is no WCAG 2.1.2 trap to avoid. The mirror trade-off: the page's own Tab order is unreachable from the keyboard (#126), IME composition waits on gocef's binding (#121), and a page animating while scrolled out of a `Scroll` keeps CEF compositing (#128).
  - **The engine travels with the app, not the OS** — the deliberate exception to the every-backend-uses-the-platform-engine policy. `belluikit/gocef` (BSD-3, tagged) binds CEF's **C API** via a dlopen'd `libcef.so` — nothing links at build time, so `go build` is hermetic on machines with no payload; `belluikit/gocef-libs` mirrors the pinned build (`manifest/manifest.go` is the pin and CVE-response path, #98 owns the cadence) and **`bellui package` lays it out (#107, shipped)**: a linux target whose executable's build info lists `belluikit/gocef` gets the pinned payload fetched (manifest SHA-256 verified on every use, empty hash refused; plain URL first, `gh release download` while the mirror is private), cached under the user cache, and unpacked to `bin/cef` — the `gocef.Locate` packaged layout — with Makefile install/uninstall/user-install blocks carrying it. E2E-verified on trader: package → `make install` → the installed binary runs the full probe with no `BELLUI_CEF_DIR`.
  - **The sandbox decision (#107, recorded and implemented).** gocef ≥v0.3.0 exposes `Config.SandboxPath` (empty = `no_sandbox`, the old hard-coded state; non-empty = exported as `CHROME_DEVEL_SANDBOX` + sandbox on). The backend's policy in `resolveCEFSandbox`: **in a Flatpak, off with no complaint** (bubblewrap already isolates; a Flatpak cannot ship setuid, and a mis-tagged flatpak still lands right because the ownership gate fails inside the container); **outside, on exactly when `<payload>/chrome-sandbox` is root-owned setuid** — which the packaged Makefile's `make install` sets up best-effort — **otherwise off with a logged notice**, never a guess: with the sandbox enabled and no usable helper (user namespaces restricted, as on recent Debian/Ubuntu), Chromium aborts the process rather than reporting an error. Measured both ways on trader: root-SUID helper → renderers run `Seccomp: 2` with no `--no-sandbox`; user-owned → `--no-sandbox`, `Seccomp: 0`, and the notice names the fix. Discovery: `BELLUI_CEF_DIR` → `<exe>/cef` → `<exe>`; absent → `webview.ErrRuntimeMissing` and an inert host, the same degradation as a missing WebView2. `BELLUI_CEF_SWITCHES` / `BELLUI_CEF_LOG` are the deployment/diagnostic seams. **Profile (#125): persistent by default** at `Storage().RootURI()/webview-cef` — matching every other backend's platform-managed persistence — with `webview.SetCEFProfileDir` / `SetCEFProfileInMemory` as the pre-first-Attach knobs (portable declarations, Linux-only effect; late calls error, never a silent no-op). Under the hood gocef ≥v0.2.0 binds *both* CEF paths: `cache_path` (the profile; empty = incognito, which is why #105's empty-string default never persisted anything) and `root_cache_path` (installation data + the CEF 120+ process-singleton lock; left empty CEF falls back to the `~/.config/cef_user_data` directory **shared by every CEF app on the machine** — the singleton warning #125 settled). In-memory mode still sets a fresh per-process temp root so instances never contend; a second instance of an app sharing a persistent profile dir fails Initialize permanently and its hosts go inert, the documented degradation — single-instance mode, per-instance dirs or in-memory are the outs. One measured gap remains: the backend never calls CefShutdown and no flush is bound, so a cookie set in the final ~30s before exit is lost (localStorage's leveldb commits sooner and survives) — #134 owns binding `flush_store` and picking the flush seam; until then `cefhostprobe -profile write` settles 35s by default.
  - **Once-per-process, one thread**: CEF initializes on the first `Attach` from the main goroutine (which the driver keeps locked to the main OS thread — every CEF call must come from the thread that initialized it, #117's hardest-won lesson), is pumped by a repeat-forever `bellui.Animation` that runs only while browsers exist, and is **never shut down** — re-init is impossible, so process exit reclaims it. All callbacks arrive inside `gocef.Work()` on the main goroutine, which is what makes the backend main-goroutine by construction. Under the **test driver**, animations tick exactly once — a headless probe must pump `gocef.Work()` itself (`hack/cefhostprobe` does).
  - **The bridge rides CDP from the browser process** (a native route would need renderer-side code; `CefMessageRouter` is C++-only): `Page.addScriptToEvaluateOnNewDocument` injects the shim at document *start* (better than Android/wasm) — but **only if `Page.enable` was sent; without it the injection silently never fires** (measured, no error anywhere); `Runtime.addBinding` is the `/*POST*/` transport, with per-frame origins from `Runtime.executionContextCreated` reduced through `serializeOrigin` (opaque arrives as `"://"`); `Runtime.evaluate` carries `exceptionDetails`, so Linux does **not** inherit the null-on-throw defect (#83). Bridge off → none of that is installed, per the contract. Navigation stays on CEF's native API (gocef `LoadHandler`/`NavigationHandler`; `ERR_ABORTED` filtered as already-accounted-for; popups are always refused shim-side and an allowed `NewWindow` loads in place). Creation is asynchronous, so pre-ready calls queue and replay in order — the Windows answer to the same shape. `LoadHTML` is a data: URL (CEF has no load-string): baseURL ignored, origin opaque, as on Windows.
  - **CEF's OSR coordinate contract**: `GetViewRect` and input events are in **points** (bellui's units, 1:1), paint buffers in **pixels** (points × the `device_scale_factor` from `GetScreenInfo` — the canvas scale, re-captured each layout, which a monitor change re-runs). That contract only holds because **the CEF process is pinned to ozone-x11 whenever `DISPLAY` is reachable** (#139, `cefOzonePlatformSwitches`): ozone-wayland caps the page's `devicePixelRatio` at min(client answer, `wl_output` scale) and ignores `--force-device-scale-factor` (crbug 40604649) — measured across mutter, `weston --scale=2` and XWayland; upstream CEF likewise steers OSR to forced x11 (cef#3953). CEF opens no visible windows here, so its platform is free to differ from the session bellui runs on; the pure-Wayland fallback (no XWayland) keeps working with that HiDPI cap as a recorded Chromium limitation, and an explicit `--ozone-platform` in `BELLUI_CEF_SWITCHES` always wins. `<select>` dropdowns arrive as a second `PET_POPUP` surface that must be composited over the view or they are invisible; frames go through a two-slot ring so the painter never reads a buffer being written. The CPU copy+swizzle measured 1.9 ms at 1080p (`hack/cefprobe`); dirty-rect upload is #99, dma-buf import #113.
  - **`webview.NewHost` returns the portable `*webview.Host`** spanning both hosting models (breaking; the package is Since: 2.19) — `widget.NativeViewHost` inside on hole-punch platforms, the composited host on Linux, with focus/min-size/sync-stats delegated. `widget.NewNativeViewHost` is unchanged for direct users.
  - **Verify**: `hack/cefhostprobe` (headless — test app + software renderer + its own pump; needs `BELLUI_CEF_DIR`) passed 13/13 on trader against the pinned payload: composition with an overlay above, document-start shim, both bridge directions under an opaque-origin policy, exception-carrying eval, input round-trips, veto, teardown. `libcef.so` needs the ATK/AT-SPI libs present or dlopen fails. The live-session sweep — GPU painters, X11+Wayland indistinguishability, popups, HiDPI, real-driver input — is #127. gocef itself is integration-verified against a real Chromium on every push in its own repo.

- **Backends shipped** — macOS (`webview_darwin.*`, the reference), **wasm (#62)**, **iOS (#64)**, **Android (#63)**, **Windows (#65)** and **Linux (#105** — composited, not a hole punch; see the block above**)**. Each bends the API where its engine does, and every difference is documented on the backend that has it: on **wasm** the bridge/`Eval`/`Call` reach same-origin content only, `OnNavigate` sees only the loads this package starts (a browser exposes no navigation-policy hook for an iframe) and `CanGoBack`/`CanGoForward` report false (an iframe shares the top-level session history); on **wasm and Android** the page-side shim is injected at document *load*, not document start (neither offers a user-script hook), so a page's own first lines may not see `window.bellui` — `LoadHTML` on wasm is the exception, carrying the shim in the `srcdoc` markup itself; on **Android and Windows** neither `evaluateJavascript` nor `ExecuteScript` has a channel for a thrown exception, so a throwing script reports null rather than an error — which also means a `Call` against a page with no shim stays pending on those two instead of failing at once; on **Windows** `LoadHTML` ignores its `baseURL` (`NavigateToString` is the whole literal-content API, so such a page always has the opaque origin) and a user-started navigation is always reported as `NavigationLinkClicked` (WebView2 reports *that* the user started it, not *how*). **iOS hosting is a sibling of the GLKView in the app window, never a subview** (#1124 — CAMetalLayer entanglement stalls rendering), deliberately the opposite of macOS, where the clip view *is* a subview of the GLFW content view and composites cleanly; iOS `RunNative` hands out only an `UnknownContext`, so the window is reached through a `belluiAppWindow()` accessor in the driver's `darwin_ios.m` (the same cross-package ObjC extern pattern `accessibility_ios.m` uses). **Android** must keep its Java in `GoNativeActivity.java` (a WebView needs real Java subclasses and a `@JavascriptInterface` object, unbuildable from JNI), so that half ships in every app's dex while the Go half stays an optional import; its JNI up-calls are defined in the `webview` package and found by JNI's name-based resolution across the process image (an app that never imports it just leaves them unbound). Android down-calls all post to the UI thread via `runOnUiThread` (order-preserving, so nothing blocks), and the synchronous queries (`canGoBack`, `hasFocus`) read **shadow state** kept current on the UI thread rather than round-tripping — that is what keeps the per-frame focus poll off the #973 deadlock path; the one exception is the navigation policy, where `WebViewClient` blocks on the answer so it goes through `DoAndWait`. **Touching `GoNativeActivity.java` requires the tools-repo dex regen.**
- **Android IME & panel-focus arbitration (#76 → #143, measured on OPD2403 + stock Pixel API 34 emulator).** The panel window (`TYPE_APPLICATION_PANEL`, named `BelluiWebViewPanel` in dumpsys) starts `FLAG_NOT_FOCUSABLE` and is promoted/demoted by exactly two signals: a touch in the web area promotes, the focus bridge's resign demotes — because an attached sub-window that is focusable holds the app's window focus outright (the #76 platform law; leaving it focusable starves bellui's keyboard).
  - **The touch hook MUST be the panel's `dispatchTouchEvent`, never an `OnTouchListener` on the clip**: a ViewGroup's own touch listener runs only when no child consumes the event, and the WebView consumes every tap — #143's first instrumented run showed taps inside the panel producing no listener callback at all, which was the entire cold-tap failure class (#76's "unreliable on this OEM" was the promote never firing; any successes were warm state left by programmatic promotions).
  - **The gesture race is universal, not OEM policy**: on both stock AOSP and ColorOS, the in-place `updateViewLayout` flag promotion transfers window focus in ~35–45 ms — always after a real tap's UP — so the editor-focusing gesture is always spent by Chromium's fresh-gesture IME rule, and the delayed replay (`dispatchTouchEvent` of a synthetic down/up at the tap point, 250 ms + 800 ms fallback) is what raises the keyboard *everywhere*. Verify both legs with `hack/androidwebviewprobe/drive.sh coldtap` (15/15 stock, 13/13 OPD2403 after the fix; before it, 0/N cold taps could summon the keyboard).
  - **The replay is guarded against phantom clicks** (defects that became reachable once the hook actually fired): only a gesture within touch slop schedules a replay (a scroll/fling must not become a synthetic click at its start point), and the replay itself is skipped unless `InputMethodManager.isActive(web)` — Chromium hands the IMM an `InputConnection` only while an editable element is focused, so a tap on a link or plain content is never re-dispatched.
  - **The #143 trace ships in every dex, off by default**: `adb shell setprop log.tag.BelluiWebView DEBUG` turns on logcat lines for every window-focus transition on both windows, promote/demote decisions, replay firings with skip reasons, and IME inset visibility; `WebView.setWebContentsDebuggingEnabled` rides the same gate (chrome://inspect for `ImeAdapter` state). Correlate with `dumpsys input_method` (`mInputShown`) as ground truth.
  - **Keystroke latency: no backend cost, measured.** In-page per-keystroke numbers (keydown `event.timeStamp` delta = delivery, input→rAF = paint) via the probe's `latency` mode, single-char injection (a 20-char `input text` burst measures queue wait, not latency — p50 ~90 ms vs ~2 ms per-char): OPD2403 delivery p50 1.7–2.1 ms, paint p50 9.2–9.4 ms, p90 ≈15 ms — frame-cadence-normal, and statistically identical across debug vs release (`-w`, trimpath) builds and spinner on vs off (the stall-spinner is a separate window's surface, so it never was backend cost). The #143 "visible per-keystroke delay" report does not reproduce under measurement; the plausible original culprit is typing into the degraded pre-fix IME state.
  - **`bellui package --release` gotcha discovered en route**: the flag only strips the Go binary — `buildRelease` is wired to `distribution`, so the manifest keeps `android:debuggable="true"` and debug targetSdk (see the follow-up issue). Also: a stale `bellui` CLI binary carries a stale embedded dex — always rebuild the CLI from the checkout after touching `GoNativeActivity.java` (drive.sh build does).
