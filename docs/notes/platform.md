# Platform Integration (desktop/mobile/web)

Fork-specific design detail for this area. Issue numbers refer to the Bellui
Backlog.

### File Dialog Enhancements
- `(*dialog.FileDialog).SetShowHidden(bool)` / hidden files toggle — exposes control over hidden file visibility
- `storage.IsHidden(bellui.URI)` — the per-platform hidden-file convention behind that toggle as public storage API (Unix dot-prefix, Windows hidden attribute, mobile/wasm always false); the dialog and `widget.FileTree` both use it (pre-rebrand tracker #445, pre-rebrand tracker #455)
- **Touch multi-select — selection mode (#259)**: long-pressing a file item in the canvas dialog's open-multiple mode enters selection mode; plain taps then toggle set membership, the double-tap open shortcut is suspended (its second tap just changed the set it would confirm), and the confirm button reports the set as usual. Escape/Back leaves the mode first — clearing the whole set, including anything added by Ctrl/Cmd-click, the leave-selection-mode-drops-the-selection convention — and only the next press cancels the dialog. Deselecting the last file ends it too; that tap is still a selection-mode tap (`Tapped` reads the mode *before* the toggle runs), so it can neither arm nor fire the double-tap open. Closing the dialog by any path — Cancel, the windowed frame's X, confirm, the host window closing — also ends the mode, so a re-`Show` never reopens with plain taps still toggling (the selection set keeps its own persistence). It composes with the pointer modifiers rather than replacing them (Shift keeps range precedence from the long-press anchor, Ctrl/Cmd toggle is indistinguishable from the mode's own), and it survives navigation, like the selection set. Delivery is the hold-fire long-press (pre-rebrand tracker #758): `LongPressed` fires while the finger is still down and the release of a hold-fired touch never delivers `Tapped`, so the entering hold cannot toggle its own selection back out (locked by `internal/driver/mobile/canvas_longpress_modal_test.go`). With it, the mobile driver routes Android's Back through `intdriver.HandleEscape` ahead of `KeyBack` delivery — Back backs out of the mode, then the dialog, then reaches the app. The mobile-picker gap is closed (#267): the pickers honour `UseNativeFileDialogs(false)`, so the canvas dialog — and with it on-device probing of the gesture — is reachable on a packaged device build. The GLFW gap (#266) is closed by two complementary paths: the driver hold-fires `LongPressed` on a stationary primary press (mouse, and touch wherever it is pointer-emulated — X11/macOS; the widgets.md LongPressable note carries the decision record), and Windows/Wayland desktop touchscreens deliver real touch through the glfw fork's touch callback into the mobile gesture pipeline (belluikit/glfw#1, v1.10.0; see docs/notes/widgets.md, "Desktop touchscreen gesture dispatch"). Because press-and-hold makes a *slow mouse click* reach the gesture, a hold the dialog declines — single-select, or a directory — falls back to `fileDialogItem.Tapped`: `enterSelectionMode` reports whether it entered, and with the driver's `Tapped` already withheld the item would otherwise eat the click (select nothing, navigate nowhere).

### Native / Portal File Dialogs (pre-rebrand tracker #514)
`dialog.UseNativeFileDialogs(bool)` — global opt-**out**; the platform-native picker serves `FileOpen`/`FileSave`/`FolderOpen` by default (#226) and the canvas-drawn dialog is the fallback, behind the **existing** `fileOpenOSOverride`/`fileSaveOSOverride` seam (`file.go:1089/1096/1311/1354`, `folder.go:35`; an override returning `true` skips the canvas UI, `false` falls back to it — that *is* the "never lose the feature" guarantee). Same `dialog.File*` API, same `bellui.URIReadCloser`/`URIWriteCloser`/`ListableURI` results, so app code is unchanged. `nativeFileDialogsFor` adds one condition beyond the toggle: the dialog's parent must implement `driver.NativeWindow`, since a native picker needs a platform window to sit over — that is also what keeps the test driver (and therefore `go test ./dialog/` on a machine with a real session) on the canvas dialog. The wasm overrides mirror exactly that window check (`browserWindowFor`, #257): the web driver's window implements `driver.NativeWindow` (delivering `driver.BrowserWindowContext`, which carries the window's `<canvas>`), an emulated extra window delegates to the root it embeds (explicitly — embedding the `bellui.Window` interface would not promote the method), and the test driver's windows fail the assertion, so a js/wasm test binary is served by the canvas dialog instead of clicking a real `<input type="file">` or triggering a real download in the harness page. The native call runs in a goroutine and marshals the result back with `bellui.Do` (copy the async idiom in `file_xdg_portal.go`). That same delivery hop fires `SetOnClosed` via `FileDialog.notifyClosed` — immediately before the result callback, `true` only on a confirmed choice, mirroring the canvas dialog's order. The mobile and wasm-open overrides report the same way (#233; mobile queues the platform-thread picker result to the main goroutine in the same hop; a platform app without a picker — or, since #267, the toggle being off — makes the mobile override return `false`, falling back to the canvas dialog rather than silently dropping the request). On browsers that never fire `cancel` on `<input type="file">`, the wasm open picker falls back to a window-refocus + grace-period heuristic (`pickerDismissGrace`) so a dismissal still reports — known costs: an early dismissal report if a non-window-modal picker lets the user refocus the page mid-pick, and a choice whose `change` event trails the refocus by more than the grace period is dropped (the dismissal has already been reported; `finish` detaches the input's listeners before releasing their funcs, so the late event finds no listener rather than a released `js.Func`). wasm **save** is the one deliberate deviation: the writer is handed out immediately and the "dialog" is the download offered at `Close` (idempotent — a deferred `Close` alongside an explicit one neither re-downloads nor re-reports), so `notifyClosed(true)` fires at writer close — *after* the result callback, and never if the app abandons the writer.
- **Linux/BSD (Phase 1, done)** — `org.freedesktop.portal.FileChooser` over D-Bus via `github.com/rymdport/portal` (BSD-3, already a dep); works both sandboxed (**the only correct path under Flatpak/Snap** — the in-canvas dialog browses an empty sandbox) and unsandboxed (the portal falls through to the desktop's own GTK/Qt dialog). `file_xdg_portal.go` (tag `(linux||openbsd||freebsd||netbsd) && !android && !wasm && !js && !tamago && !noos`) is the generalization of what used to be the `-tags flatpak`-only path. A cached D-Bus `NameHasOwner("org.freedesktop.portal.Desktop")` probe (`portalReady`) gates it: **no portal on the bus → override returns `false` → canvas fallback**. **Flatpak builds always use the portal regardless of the toggle** (`build.IsFlatpak` forces `nativeFileDialogsEnabled()` true; the probe is skipped since the sandbox always provides one). X11 window parenting via `RunNative`→`X11WindowContext`; Wayland parenting (`xdg_foreign`) is a TODO (unparented for now).
- **macOS (Phase 2, done)** — NSOpenPanel/NSSavePanel via an MRC ObjC cgo bridge (`file_darwin_native.{go,m,h}`): sheet-modal over the parent `NSWindow` (`RunNative`→`MacWindowContext`), `//export`ed completion handler wraps the path and fires the typed callback via `bellui.Do`; `UTType` filters (ext + MIME on macOS 11+).
- **Windows (Phase 3, done)** — the modern Common Item Dialog (`IFileOpenDialog`/`IFileSaveDialog`) driven **purely through `x/sys/windows` COM syscalls, no cgo** (`file_windows_native.go`). CLSID/IID `windows.GUID` literals + hand-written vtable slot offsets (IUnknown→IModalWindow→IFileDialog; both dialogs share the `IFileDialog` base so `GetResult` covers single-select open + save); `ole32.dll` `CoCreateInstance`/`CoTaskMemFree` + `shell32.dll` `SHCreateItemFromParsingName` (for `SetFolder`). Runs on a dedicated `runtime.LockOSThread`'d goroutine (never unlocked → the STA COM apartment lives and dies with the goroutine; `Show` pumps its own modal loop) with `CoInitializeEx(APARTMENTTHREADED)` (skips the balancing `CoUninitialize` only on `RPC_E_CHANGED_MODE`); result marshalled back via `bellui.Do`, mirroring portal/macOS. Parent `HWND` best-effort via `RunNative`→`WindowsWindowContext.HWND` (0/unparented is fine — Show blocks either way; cross-thread owner isn't auto-disabled, acceptable for v1). Filters → `COMDLG_FILTERSPEC` (`*.ext;…`); MIME filters have no native Windows concept so they're best-effort mapped via `mime.ExtensionsByType` (unmappable → all files). **cgo-free pointer hygiene**: the `comCall` helper stashes args in a `[]uintptr`, which forfeits the `//go:uintptrescapes` liveness guarantee (that only holds for `syscall.SyscallN`/`LazyProc.Call` with the conversion *in* the call expression, as the direct `Show`/`GetResult`/`CoCreateInstance`/`SHCreate…` calls use) — Go's GC is non-moving so addresses stay valid, but every Go pointer handed through `comCall` is pinned in a `pins []any` kept alive to end of function.
- **Canvas-only caveats**: `SetShowHidden` is not expressible on the native surfaces — documented as canvas-dialog-only. Multi-selection *is* honoured natively for file-open — macOS NSOpenPanel (pre-rebrand tracker #716), the Windows dialog, the portal, and the mobile pickers (#255) — with an environment lacking a multi picker declining into the canvas dialog (pre-rebrand tracker #627), where the long-press selection mode (#259, above) is the touch entry. Mobile keeps its native pickers (`file_mobile.go`) but since #267 they honour `UseNativeFileDialogs(false)` — a gate at the top of both overrides, settling the contract in favour of the toggle's "everywhere" doc: the canvas dialog browses something real on mobile (app-scoped storage), so an explicit opt-out must not be a silent no-op, and it is also what makes the canvas dialog (and on-device probing of #259's gesture — `filedialogprobe`'s native-pickers check) reachable on a packaged device build. The recorded cost, in the `UseNativeFileDialogs` doc: the platform picker is the only surface reaching outside the sandbox on modern mobile, so opting out for desktop-consistency reasons should be platform-gated by the app. wasm is the one deliberate holdout — the toggle is ignored there because a canvas dialog has no real filesystem to browse in a browser (`file_wasm.go` — `<input type=file>` for open, Blob download-on-`Close()` for save (pre-rebrand tracker #625); since #257 the wasm overrides require a real browser-hosted parent window (`browserWindowFor` above) — the test driver falls back to the canvas dialog; directory-open falls back to the canvas dialog).

### Android In-Process Activity Recreation (#283)

Any configuration change the manifest does not declare makes Android destroy and
recreate the activity **inside the surviving process** (guaranteed trigger: an
Android 13+ per-app locale override, `cmd locale set-app-locales`; also display
density/size changes). The gomobile lifecycle plumbing survives this fine —
`activityDestroyed` → StageDead → the recreated activity re-crosses to
StageFocused; #283's original "the driver treats StageDead as terminal" theory
was **wrong**, disproven by goroutine dumps.

- **Root cause of the #283 ANR (WebGPU only)**: the destroy→create gap overlaps
  queued paint ticks — the lifecycle re-cross refreshes the canvas — so the
  painter **presented Vulkan frames into the just-destroyed ANativeWindow**,
  then `Device.RecreateSurface`'s `GetCapabilities` on the new window never
  returned. The Java main thread was meanwhile parked in gomobile's
  `onNativeWindowRedrawNeeded` handshake waiting for a first frame → ANR. The
  GL path was never affected: mainUI destroys the EGL surface synchronously in
  its `windowDestroyed` case and `Publish` checks `C.surface`.
- **Fix**: `app.NativeWindowLive()` — an atomic written only by mainUI (false on
  `onNativeWindowDestroyed`, true on `onNativeWindowCreated`/`RedrawNeeded`).
  The Android WebGPU backend gates `renderReady` on it (whole frames skip while
  the window is dead — the handle alone can't express this, it stays stale until
  the recreated activity's paint event replaces it) and `presentPainter`
  re-checks it last-moment, abandoning the open frame (`painter.AbandonFrame`,
  the #337 dangling-SurfaceOutput discard) instead of presenting. Late *release*
  of the dead window's surface is harmless (the plain background→resume path
  has always done it); only the *present* poisons.
- **Emulator diagnostic gotcha (goldfish)**: one bad present wedges the
  emulator **host process's** GPU channel permanently — after that, every app
  launch hangs in `wgpuCreateInstance` (black screen → ANR on any start, which
  is what the issue misread as "any launch with an override ANRs"), and a
  **guest reboot does not clear it — only restarting the emulator process
  does**. If pixel143 starts hanging every bellui app at launch, restart the
  emulator before debugging anything else.
- **Manifest**: the packaging template declares `locale|layoutDirection` in
  `configChanges` (and `screenLayout` since #299, below) — the framework adds
  `layoutDirection` to every locale change mask, so both are required for an
  Android 13+ per-app language change to arrive as `onConfigurationChanged`
  instead of an activity recreation (#283). Declaring it needed the #287 regeneration of the CLI's
  embedded binres SDK table (now pinned via `binres.SDKPlatform`, recorded in
  the generated arsc.go header); since #287 an unknown `configChanges` flag
  name is a hard manifest-compile error instead of a silently dropped bit.
  Live in-place locale pickup rides this delivery (#288): the native
  `onConfigurationChanged` callback forwards a `config.Event`
  (`internal/driver/mobile/event/config`) through the app event queue — the
  send is unbounded, so the Java main thread never blocks — and the driver's
  event loop answers it with the #282 `lang.ResolveSystemLocale` re-resolve
  seam on the driver goroutine. So a per-app language change on a foregrounded
  app applies (relayout included) with no recreation and no lifecycle
  crossing; the StageFocused re-resolve remains the pickup for changes made
  while backgrounded. Every other declared change lands on the same path
  (rotation — whose config event precedes the redraw — plus `uiMode`,
  `keyboardHidden`, and `keyboard`, which since #793 keeps a hardware keyboard
  being plugged in from relaunching the activity), which is fine but not free: the re-resolve is
  override-guarded and skips the relayout while the locale is unchanged, yet
  it still costs a `GetLocales` JNI round trip plus a localizer rebuild on the
  driver goroutine. That cannot wedge the redraw handshake the config event
  precedes — go-locale runs the lookup through `RunOnJVM`, which attaches its
  own thread rather than borrowing the Java main thread (the deadlock shape
  the soft-keyboard `keyboardOps` worker exists to avoid) — but a future
  rotation-latency investigation should know it is there. Verified 2026-08-05
  on the pixel143 AVD (stock android-34): deviceinfoprobe prints one
  `trigger=localechange` line with the new `current=` and recreateprobe shows
  zero lifecycle lines through the change. **ColorOS 16 needs `screenLayout`
  declared too (#299)**: its
  `ActivityRecordExtImpl.hookShouldRelaunchLocked` computes
  `adjustedChanges={CONFIG_LOCALE, CONFIG_SCREEN_LAYOUT,
  CONFIG_LAYOUT_DIRECTION}` — the vendor hook adds CONFIG_SCREEN_LAYOUT
  (stock masks the layout-direction bits *out* of the screenLayout diff) —
  so with only `locale|layoutDirection` declared, OPPO/realme/OnePlus
  devices relaunched on every per-app language change. The packaging
  template now declares `screenLayout` as well, which defeats the hook: the
  A/B on the OPD2403 (2026-08-05) shows the same change arriving as one
  in-place `trigger=localechange` with zero lifecycle lines. Do not read the
  hook's `state: true` logcat line as a relaunch — it prints *before* the
  manifest check (it appears identically on a declared-mask change that then
  proceeds in place). Cost of declaring it, measured on the same device:
  masks carrying the undeclared size bits (`wm size` crossings, split-screen
  divider drags — `{CONFIG_SCREEN_LAYOUT, CONFIG_SMALLEST_SCREEN_SIZE}`;
  fold/unfold is this class) keep recreating exactly as before, while
  screen-layout-only masks (ColorOS split-screen *entry* `{CONFIG_ORIENTATION,
  CONFIG_SCREEN_LAYOUT}`, an `am task resize` bucket crossing
  `{CONFIG_SCREEN_LAYOUT}`) now arrive in place — and bellui handles them:
  the size event relayouts, deviceinfoprobe reports the new `sizePt` for the
  resized pane, ticks never stop. They join rotation in paying the config
  event's `GetLocales` round trip above, per multi-window transition rather
  than per relaunch — the cheaper half of the trade the declaration makes.
  Stock is unaffected (its locale mask never
  carried screenLayout; re-verified on pixel143 with the new manifest).
  Declaring `screenLayout` needed a binres strip fix: `PackResources`' old
  per-entry collision scan overwrote its own verdict (its `break` left only
  the innermost loop), so `id/screenLayout` — whose key-pool slot is shared
  with the dropped `^attr-private/screenLayout` — was blanked out of the
  embedded table and the flag name was unresolvable (the #287 hard error).
  The strip now blanks exactly the keys no surviving kept-spec entry
  references; `TestConfigChangesFlagNamesSurviveStrip` locks every
  configChanges flag name resolvable in the packed table.
- **Probes**: `hack/recreateprobe` (lifecycle lines + `alive=`/`tick=`
  heartbeats — at a wedge, `alive=` keeps counting while `tick=` stops);
  verified on pixel143 (goldfish) and OPD2403 (ColorOS 16, which recreates
  in-process the same way). Go-side stacks on a hung device build: add a
  `net/http/pprof` listener to the probe and `adb forward` — SIGQUIT is taken
  by ART, not the Go runtime.

### System Tray — Linux delivery caveat (pre-rebrand tracker #512)
System tray (`desktop.App.SetSystemTray*`) is delivered via **StatusNotifierItem over D-Bus** on Linux/BSD (native status items on macOS/Windows). An SNI item only appears where the desktop environment runs an **SNI host**: KDE Plasma and most Wayland compositors do; **stock GNOME shows nothing** unless the user installs the AppIndicator (KStatusNotifierItem) shell extension, and legacy **XEmbed-only** trays (some minimal WMs) are unsupported by `github.com/belluikit/systray`. This is a desktop-environment property, not a bellui bug (every non-GTK toolkit shares it). **Design rule: never make the tray the only path to a feature** — always keep a window/menu route (the "Show Window" menu-item advice). Doc'd on the `desktop.App` interface.

### Desktop Integration — Explicit Non-Goals (pre-rebrand tracker #520)
Two capabilities were reviewed during the desktop-integration gap review (multi-window pre-rebrand tracker #497–pre-rebrand tracker #499, i18n pre-rebrand tracker #503–pre-rebrand tracker #506, share/intents pre-rebrand tracker #508–pre-rebrand tracker #510, tray pre-rebrand tracker #511–pre-rebrand tracker #512, clipboard pre-rebrand tracker #513, native dialogs pre-rebrand tracker #514, DnD pre-rebrand tracker #515, notifications pre-rebrand tracker #516, polish pre-rebrand tracker #517, hotkeys pre-rebrand tracker #518) and **deliberately not pursued**, recorded here so they stop being re-litigated:
- **Printing — non-goal.** A toolkit print pipeline (pagination, print dialogs, printer enumeration, canvas→PDF) is an enormous, permanently-unfinished surface; no comparable Go toolkit ships one. **Workaround pattern**: render to an image (`software.Render` / canvas capture) or generate a PDF with a dedicated Apache/BSD/MIT library, then hand it to the OS with `bellui.OpenURL(file://…)` — the platform viewer supplies its own print UI. *Revisit trigger*: a concrete consumer whose in-app print flow the PDF handoff can't serve.
- **Session-end veto (logout/shutdown unsaved-changes prompt) — decline-unless-demanded.** `SetCloseIntercept` covers window close but not OS session end. Per-platform vetoes exist (macOS `NSApplicationDelegate` termination reply, Windows `WM_QUERYENDSESSION` + `ShutdownBlockReasonCreate`, Linux session-manager inhibitors) but modern OSes increasingly ignore or time-box them, and half-working veto UX is worse than none. **Durable answer**: crash-safe continuous state save (autosave/journal), so an un-vetoed session end loses nothing. *Revisit trigger*: a concrete, well-scoped demand.

### Runtime Wayland/X11 Selection (pre-rebrand tracker #542)
Linux display-server selection is a **runtime** decision, not a build-time one — a single default binary runs correctly on both X11 and Wayland sessions (matching upstream v2.8.0, ports `147177dcb` + the CSD heuristic `4a52a9fe8`). The old `-tags wayland` split (one X11-only binary, one Wayland-only) is gone from the default path.
- **Both backends in one binary**: the fork's `belluikit/glfw` (>= v1.2.0) compiles both C backends by default *and* exposes both Go native-accessor sets (`GetX11Window/Display` + `GetWaylandWindow/Display`) in the default build — the v1.2.0 change that unblocked this (upstream Fyne is GL-default and never needs the native surface handle; our WebGPU-default painter does, so both must be linkable). GLFW auto-selects at init.
- **`build.IsWayland` is now a runtime `var`** (`internal/build`), not a compile-time const: `false` in the default/`x11` build, set `true` in `loop_desktop.go`'s `initGLFW` when `glfw.GetPlatform() == PlatformWayland`. The ~11 existing `IsWayland` branches (positioning, content-scaling) plus the native-handle dispatch (`window_x11wayland.go` `RunNative`, `backend_webgpu_x11wayland.go` surface descriptor) key off it, so they are correct per-session. A forced single-backend build hard-codes the right value.
- **`BELLUI_PLATFORM=x11|wayland`** pins the choice via `glfw.InitHint(glfw.PlatformHint, …)` before `glfw.Init()` (`forcePlatform`, adopting upstream's env var name/values verbatim); any other value is ignored.
- **An X display alone means X11** (#534): with `DISPLAY` set and `WAYLAND_DISPLAY` unset, `forcePlatform` pins X11 instead of deferring to GLFW. GLFW 3.4 follows `XDG_SESSION_TYPE` only when it reads `wayland` or `x11`, and otherwise tries Wayland first. libwayland then falls back to `$XDG_RUNTIME_DIR/wayland-0`, so on a machine with a Wayland desktop logged in, an app started over `ssh -X` or on an Xvfb opened on that desktop instead of the display it was given. Pinned by `TestForcePlatform`. A Wayland session that has lost `WAYLAND_DISPLAY` but kept `DISPLAY` lands on XWayland, which is the accepted cost.
- **CSD heuristic** (`wayland_csd_linux.go`): on a Wayland session that *also* has XWayland (`DISPLAY` set), prefer X11 when the compositor does not advertise `zxdg_decoration_manager_v1` (no server-side decorations — e.g. GNOME/Mutter), avoiding GLFW's client-side titlebar. Probed with a one-shot `wayland-client` registry roundtrip; adds a `pkg-config: wayland-client` build dep to the default linux driver build. `BELLUI_PLATFORM` overrides it. `wayland_csd_other.go` is the no-op stub for non-runtime builds.
- **Forced builds** stay available: `-tags wayland` (Wayland-only) and `-tags x11` (X11-only) each drop the other backend for a lean binary; their dedicated `window_{wayland,x11}.go` / `backend_webgpu_{wayland,x11}.go` files have narrowed tags so they don't overlap the runtime `*_x11wayland.go` files. Live in-place toggling isn't supported (chosen once at init, like the global `SetLayoutDirection`). BSD stays X11-default (its Wayland accessors remain tag-gated in the glfw fork). Verified end-to-end on GNOME/Wayland+Mutter (auto→X11 via CSD, `BELLUI_PLATFORM` both ways) plus all four build modes compiling on arm64 linux.

### Standard Cursors — availability per backend (#269)
`desktop.StandardCursor` is mapped to a native shape once, at driver init (`initCursors` in `internal/driver/glfw/window_desktop.go`), into an array **indexed by the enum** — so a new member needs an entry there *and* a case in `window_wasm.go`'s `belluiToNativeCursor`, or it degrades silently (out-of-range clamps to the arrow; wasm falls through to CSS `default`). **A nil table entry is not "the default arrow" — it is `HiddenCursor`**: `processMouseMoved` answers a nil native cursor with `SetInputMode(CursorMode, CursorHidden)`, so a shape that fails to resolve takes the pointer away entirely. That is why the diagonals (`NWSEResizeCursor`/`NESWResizeCursor`, glfw 3.4's `GLFW_RESIZE_NWSE/NESW_CURSOR`) carry a fallback: they are the shapes most likely to be missing — X11 and Wayland load them from the cursor **theme** with no core-font/legacy name to fall back on, and Cocoa reaches them through a private `NSCursor` selector; only Win32 (`IDC_SIZENWSE`/`IDC_SIZENESW`) is guaranteed. GLFW reports `CursorUnavailable` and the fork's `CreateStandardCursor` returns nil, so `diagonalResizeFallback` substitutes the horizontal resize shape (a corner keeps *a* resize affordance), then the arrow. Locked by `TestCursors_EveryStandardShapeResolves` in the display-enabled glfw suite (`local_glfw_suite.yml`, xvfb/X11 — the leg where the diagonals actually exercise the fallback; the `ci`/`no_glfw` runs never reach GLFW init, so the table is empty there). Consumer side: the driver applies the **top-most `desktop.Cursorable`** under the pointer (the hit-test walk keeps overwriting as it goes and never stops early), which is what lets `InnerWindow`'s resize corner win over the content stacked beneath it — see `docs/notes/widgets.md`.

### Window Positioning & Screens (pre-rebrand tracker #497)
Desktop windows can be placed programmatically (upstream deliberately omits this; upstream 2.8 later added the request half, which we match). All types live in `driver/desktop`:
- `desktop.Window` — **upstream 2.8's interface verbatim** (same names/semantics so upstream fixes cherry-pick cleanly): `RequestPosition(x, y int)` (loose native-coordinate contract — "may be scaled", may span monitors; ignored on Wayland), `RequestAlwaysOnTop()` (call before `Show`; WM may ignore), `RequestFullScreenSecondary()` (fullscreen on a non-primary monitor; primary when there is only one).
- `desktop.PositionableWindow` — fork extension embedding `desktop.Window`: `Position() (x, y int)` read-back (last windowed position — unchanged while fullscreen; zero before first placement and on Wayland) and `SetOnMoved(func(x, y int))` (main goroutine; fullscreen re-seats not reported). Coordinates round-trip through `RequestPosition` verbatim, so save/restore of window geometry needs no unit conversion.
- `desktop.Driver.HasSecondaryDisplay() bool` (upstream 2.8 parity, mirroring-aware) and `desktop.ScreensDriver` — `Screens() []ScreenInfo{Name, Bounds, WorkArea, Scale, Primary}` (`ScreenArea` rects in the same native coords; `Scale` = bellui's detected per-monitor scale; call on the main goroutine). Enough for placement logic — deliberately not a display-configuration API.
- Mobile and wasm windows/drivers do **not** implement the window interfaces (assertion fails — never a silent no-op); the wasm driver reports `HasSecondaryDisplay() == false` because it claims `desktop.Driver` for pre-rebrand tracker #460.
- Ported with the interface: upstream's macOS 26 fix seating new windows on the same monitor as a visible sibling when no position was requested (`findSiblingMonitor`), and the fullscreen-target re-seat in `window_darwin.m`.

### Window-Hosted Dialogs (pre-rebrand tracker #498, Phase 1)
`Dialog.SetWindowHosted(hosted bool)` (default off; call before `Show`) opens any shared-`*dialog` dialog (information/error, confirm, custom — including `NewAbout`, which is built on it — form, color picker) in its **own native `bellui.Window`** instead of an overlay popup inside the parent canvas — so it can be moved/resized by the OS window manager and appears in the window switcher, and long content is no longer clamped to the parent window. Modality is **window-modal and pure Go**: while open, a `modalScrim` overlay (`dialog/windowhost.go`) blocks the parent canvas (tapping it re-focuses the dialog window, matching window-modal convention); other app windows stay interactive. Native close (the window's close button → `SetCloseIntercept`) and the Escape key both route to `Dismiss()`, reporting a `false` response exactly once. The window is centered over the parent using pre-rebrand tracker #497 (`desktop.PositionableWindow.Position()` + `RequestPosition`, scaled via `internal/scale`); parents without the positioning interface are left to the WM. **Mechanism**: `base.go`'s show/hide/refresh/resize seams (`showHostWindow`/`hideHost`/`refreshHost`, `hostWindowClosed`) branch on `d.hostWin`; the shared `d.body` container is re-parented into the window (`SetContent`), and `refreshHost` refreshes the body directly rather than the hidden popup (whose renderer would re-lay-out the body to popup size). A rebuild-while-shown (ColorPicker `updateUI`) re-seats the fresh body. Gated by `windowHostSupported` (const, build-tagged): single-window platforms (mobile/wasm/tamago) ignore the mode and fall back to the overlay. **`FileDialog` parity (pre-rebrand tracker #597)**: `FileDialog`/`fileDialog` are separate types with their own show/hide plumbing (the `fileDialog.win` popup, direct `win.Show()/Hide()`, popups anchored to `win.Canvas`), so they get their own host-aware seams in `dialog/file_windowhost.go` (`hosted`/`showHostWindow`/`hostWindowClosed`/`hide`/`show`/`refresh`/`resize`/`minSize`/`canvas`/`dialogParent`) mirroring `base.go`'s — `showFile` branches on `hosted()` to either wrap the modal popup or seat the UI (`d.body`) in a host window; the options-menu popup anchors at `d.canvas()`; and nested dialogs (New Folder form, Overwrite confirm, errors) open over `d.dialogParent()` (the host window when hosted) so they appear above the dialog, not behind the scrim on the blocked parent. The scrim setup is shared via free `addScrim`/`removeScrim` helpers in `windowhost.go`. `FolderOpen` inherits it (it's a `FileDialog`). **Phase 2 — native parent/owner relationship (pre-rebrand tracker #598)**: `driver/desktop.ChildWindow` (a `Window` extension: `SetParent(bellui.Window)`, optional-interface / asserted / no-op where unsupported, call before Show) gives the host window a true WM owner relationship *on top of* the Phase-1 scrim — the dialog stays above its parent, minimizes/restores with it, and is treated as owned. The glfw window stores a `parent` field; `applyParent` establishes the native relationship on the main goroutine from `Show` (after the window maps — robust for Wayland's deferred toplevel and WMs that restack on a late hint). Per-platform `doSetParentNative`: macOS `[parent addChildWindow:child ordered:NSWindowAbove]` (`window_darwin.m`); Windows `SetWindowLongPtr(child, GWLP_HWNDPARENT, parent)` (x/sys, no cgo, `window_windows.go`); X11 `XSetTransientForHint` and Wayland `xdg_toplevel.set_parent` **via the glfw fork** (`(*glfw.Window).SetX11Parent`/`SetWaylandParent`, added in **belluikit/glfw v1.3.0** — GLFW keeps the X11 `Window`/Wayland `xdg_toplevel` internal so bellui can't reach them; the bellui side is the 3-file `window_{x11,wayland,x11wayland}.go` split mirroring `RunNative`/WebGPU, runtime-dispatched on `build.IsWayland`). Window-hosted dialogs adopt the parent before Show via `adoptParentWindow` (shared `windowhost.go` + `file_windowhost.go`). No-op on mobile/web (wasm window has a no-op `applyParent`). Verified: macOS addChildWindow (integration test `TestWindow_SetParent`), X11 `WM_TRANSIENT_FOR` == parent (xprop), Windows `GW_OWNER` == parent HWND, Wayland `set_parent` executes clean. **Phase 3 — native OS-modality (pre-rebrand tracker #498)**: `driver/desktop.ModalWindow` (extends `ChildWindow` with `SetModal(bool)`, optional-interface / asserted / no-op where unsupported, call after `SetParent`) makes the window manager block input to the *parent* window while the dialog is up (title bar greyed, keyboard can't reach it) — the OS-enforced counterpart to the pure-Go scrim, which stays as the universal fallback and coexists. Plumbing mirrors the Phase-2 `SetParent`/`applyParent`/`doSetParentNative` seam: a `modal` field + `SetModal`/`applyModal` on the glfw window, applied at `Show` right after the parent relationship, and **`releaseModal` in the shared `destroyWindow`** (the single teardown funnel) re-enables a natively-disabled parent before the child is torn down — critical so a disabled Windows parent is never left orphaned when the child closes via any path (dialog dismiss, native close button, raw API). Per-platform `doSetModalNative`: **Windows** `EnableWindow(parent, FALSE/TRUE)` (x/sys, no cgo, `window_windows.go`) — clean owned-modal, re-enabled on close; **X11** `_NET_WM_STATE_MODAL` toggle via the glfw fork (`(*glfw.Window).SetX11Modal`, added in **belluikit/glfw v1.4.0**, mirroring `_glfwSetWindowFloatingX11`'s `_NET_WM_STATE` client-message/property pattern; needs the `WM_TRANSIENT_FOR` owner from Phase 2), runtime-dispatched on `build.IsWayland` in `window_x11wayland.go`; **macOS** parent-key suppression (pre-rebrand tracker #676) — macOS has no window-modal primitive for a *free-floating* window (a sheet isn't free-floating; an NSApp modal session is app-modal, blocking every window), so instead of native modality the parent `NSWindow` is prevented from becoming key/main while the dialog is up: `setWindowModalBlocked` (`window_darwin.m`) per-instance **ISA-swizzles** the parent to a dynamically-created subclass overriding `canBecomeKeyWindow`/`canBecomeMainWindow`→`NO` (original class stashed in an associated object, restored on unblock/teardown), so the keyboard can't reach the parent and its title bar greys inactive; `addChildWindow` ordering + scrim cover stacking and mouse. Verified by `glfw.TestWindow_ModalBlocksParentKey` via the `isWindowModalBlocked` introspection helper; **Wayland** `xdg_dialog_v1.set_modal` via the glfw fork (`(*glfw.Window).SetWaylandModal`, added in **belluikit/glfw v1.5.0** — vendors the `xdg-dialog-v1` protocol, binds the `xdg_wm_dialog_v1` global, attaches a per-toplevel `xdg_dialog_v1`; compositors that don't advertise the protocol leave the scrim as the only blocker), runtime-dispatched on `build.IsWayland` in `window_x11wayland.go` (pre-rebrand tracker #678). The dialog layer enables it via `adoptModal` in `showHostWindow`, beside `adoptParentWindow`. No-op on mobile/web. The Windows/macOS block (a *single shared parent* state, unlike X11/Wayland's per-child protocol state) is **ref-counted per parent** (`blockParentModal` in `window_desktop.go`, `modalChildren`/`modalBlockApplied` fields): it toggles the native block only on the 0↔1 transition, so two window-hosted modals over one parent keep it blocked until the last clears (pre-rebrand tracker #682). Tests: `dialog.TestAdoptModal`, `glfw.TestWindow_SetModal`, `glfw.TestWindow_ModalRefCount`, `glfw.TestWindow_ModalStackedBlocksParentKey`.

### Multi-Window Semantics per Platform (pre-rebrand tracker #499)
`App.NewWindow` behaves differently per platform, now documented on the `bellui.App`/`bellui.Window` interfaces:
- **Desktop** (`internal/driver/glfw`, `GOOS != js`) — each window is a real, independent OS window (`gLDriver.createWindow`); any number shown concurrently.
- **Web/wasm** — the **first** visible window owns the single browser `<canvas>`; **additional** windows are emulated as draggable `container.InnerWindow`s inside a `container.NewMultipleWindows()` overlay (`glCanvas.webExtraWindows`) on the root canvas — concurrent, movable/closable, but not separate OS windows (glfw-js `CreateWindow` would append a second `<canvas>` to `body`, which bellui avoids by routing extra windows through `CreateWindow`'s `js` branch → `wrapInnerWindow`). Verified via a headed-Chrome probe: a 2nd `NewWindow().Show()` opens a floating in-canvas window with full chrome, single `<canvas>` in the DOM.
- **Mobile** (`internal/driver/mobile`) — a **stack**: only the topmost *visible* window shows (`driver.currentWindow()` scans back-to-front for the first visible; the event/paint loop always targets it). A window opened over a visible one is a **child** (`isChild`, gets a titlebar with a back/close button); closing/hiding it pops back to the previous. `Test_mobileDriver_MultiWindowStack` locks this in. (Note: `mobile window.Close()` removes itself from `bellui.CurrentApp().Driver()`'s list, not its own driver's — correct in a real app with one driver, but a bare test driver must use `Hide` to exercise pop-back.)

No behavior was degenerate (no panic/blank), so pre-rebrand tracker #499 was verify-and-document, not fix. True per-window OS canvases on web (one `<canvas>` each) is a deliberate **non-goal** (large, low demand).

### Single-Instance Mode (pre-rebrand tracker #509)
`bellui.SingleInstanceApp` — an **opt-in** optional interface (asserted from the `App`, like `CloudApp`/`NotifierApp`) that enforces one running process per app **UniqueID** and forwards a second launch's command-line arguments to the primary instead of opening a second copy. It is the desktop building block behind OS file-association / URL-scheme handling (pre-rebrand tracker #510), where "open with MyApp `<file>`" relaunches the binary with the target in argv.
- `SetSingleInstance(onOpen func(args []string)) (primary bool, err error)` — call **after `NewWithID`, before `Run`**. Returns `primary`; when `false` the args (`os.Args[1:]`) have already been forwarded to the running primary and the caller should exit (no driver/window exists yet → no window flash). `onOpen` fires on the **main goroutine** (via `bellui.Do`) with the forwarded args from each redirected launch — this is the seam pre-rebrand tracker #510 layers `OnFileOpened`/`OnURLOpened` onto. Idempotent; errors without a unique ID. Method lives in `app/single_instance.go` (shared: ID guard, main-goroutine dispatch, wire protocol `readArgs`/`writeArgs` = 4-byte length + PXF `instancepb.ForwardedArgs`, which still reads the JSON array sent before #523, 1 MiB cap); `Quit()` closes the endpoint via `a.siCloser`.
- **Arguments arrive byte for byte (#661).** A Linux file name need not be UTF-8 (a Latin-1 `caf\xe9.txt`), and Linux does not record its encoding. PXF refuses invalid UTF-8, and replacing bad bytes with U+FFFD (what JSON did) names a file that does not exist. So `writeArgs` escapes each argument (`escapeArg`): valid UTF-8 is kept, and each byte that is not, or that belongs to a code point in U+EF80..U+EFFF, becomes U+EF00+byte. `readArgs` reverses it for PXF messages only. The mapping is part of the wire format and never changes (`TestForwardedArgs_EscapeForm`). The field stays a string, so a running copy of another version still reads the message: it just sees the escapes, and opening that one name fails as it did with U+FFFD. Displaying such a name still shows U+FFFD; the bytes are for opening the file. Windows gains nothing: Go already replaces invalid UTF-16 in `os.Args`.
- **Unix transport** (`single_instance_unix.go`, linux/darwin/bsd, not android/ios/wasm): primary election via an **advisory `flock`** on a per-user lock file (`$XDG_RUNTIME_DIR`, else `os.TempDir()`, 0600, uid + fnv(id) in the name). flock is atomic (exactly one racer wins) and the kernel **releases it on process death**, so stale-lock recovery is free — no liveness probing. The Unix domain socket beside the lock is used **only for forwarding**; the elected primary removes any stale socket left by a crashed predecessor before binding. **Lesson**: an earlier socket-existence election was racy — `net.Listen` does `bind()` then `listen()` as separate syscalls, so a liveness probe landing in that window gets `ECONNREFUSED` and wrongly unlinks a *live* socket → two primaries (caught by `TestSingleInstance_RaceConvergence` only under `-tags ci`/no-race fast scheduling, not under `-race`). flock is the sound primitive.
- **Windows transport** (`single_instance_windows.go`): classic named **mutex** (`Local\` namespace, atomic create → creator is primary, `ERROR_ALREADY_EXISTS` → secondary) for detection + **named pipe** (go-winio, MIT — now a direct dep) for forwarding, DACL-restricted to the current user SID + SYSTEM + Administrators. Type-checks for windows/amd64 (pure-Go winio + `x/sys/windows`); **runtime verification on a real Windows session is the follow-up** (can't drive two processes over the session-0 SSH window-station — see pre-rebrand tracker #487 gotcha).
- **Other platforms** (`single_instance_other.go`, mobile/wasm/exotic): no-op that reports `primary=true`, callback never fires (inherently single-instance).
- **macOS note**: Launch Services normally activates the running instance and delivers `odoc`/`GetURL` Apple Events rather than relaunching, so forwarding is rarely exercised there — but the detection API behaves identically (uniform Unix impl).
- Live-verify: `hack/singleinstance` (`go run ./hack/singleinstance` = primary + window; a second `go run ./hack/singleinstance <args>` forwards and exits; primary logs to `$TMPDIR/bellui-si-probe.log`). Verified with a real **two-process** test on macOS (separate PIDs, args forwarded across the process boundary and delivered on the primary's main goroutine).

### Open-With Events — File/URL Launch & Deep Links (pre-rebrand tracker #510, Phase 1)
`bellui.OpenHandlerApp` — an **opt-in** optional interface (asserted from the `App`, like `SingleInstanceApp`) for the receive half of OS "open with" / file-association / custom-URL-scheme handling: `SetOnFileOpened(func(bellui.URI))` and `SetOnURLOpened(func(*url.URL))`. Both fire on the **main goroutine**; register before `Run`. A payload arrives either as the **launch reason** (buffered and delivered once the app is running) or **while already running**.
- **Delivery model** (`app/openevent.go`, shared): payloads buffer in `pendingOpens` until the app is `running` *and* a matching handler is set; `startOpenDelivery()` (called from `Run` before `driver.Run`) flips `running` and flushes; a late `SetOnXOpened` also flushes. Delivery hops to the main goroutine via `queueOnMain` = `go bellui.Do(fn)` — the `go` matters: `bellui.Do` from the main goroutine *before* the loop starts executes **synchronously** (loop.go's `!running && IsMainGoroutine()` shortcut), so a bare call would fire the launch callback too early; the goroutine forces it to enqueue and fire once the loop pumps.
- **Classifier** (`classifyOpenArg`): skips `-`/`--` flags; a real URL scheme (`http`, `mailto`, custom `myapp:`) → URL; `file://`, bare or absolute path → file. **Windows drive letters** (`C:\...` parses as scheme `"c"`) are guarded by `isWindowsDrivePath` and treated as files. Non-flag positional argv is treated as an open target, so an app that also has its own positional CLI args should be aware.
- **Platform delivery** (`platformLaunchOpen`, one per build via disjoint tags): **non-macOS desktop** (`openevent_desktop.go`) parses `os.Args[1:]`; **macOS** (`openevent_darwin.{go,m}`) registers `NSAppleEventManager` `kAEOpenDocuments` (odoc) + `kAEGetURL`/`kInternetEventClass` (GURL) handlers (the `'GURL'` FourCharCodes are `#define`d — not in the CoreServices umbrella header) **and** parses argv (harmless for a Finder launch, which carries none); **wasm** (`openevent_wasm.go`) reads `window.location`; **ci/mobile/other** (`openevent_other.go`) no-op.
- **Already-running desktop path composes with pre-rebrand tracker #509**: `SetSingleInstance`'s forwarding now routes through `onForwardedArgs`, which fans out to both the app's own single-instance callback *and* `dispatchOpenArgs`. So on Windows/Linux an app that enables single instance (which it does anyway to avoid a second copy) gets already-running "open with" **for free** — no hidden auto-enable (that would forward a secondary's argv without giving the app the `primary` bool it needs to exit). On **macOS** the already-running case is automatic via Apple Events (Launch Services re-activates the instance; the glfw event loop **does** pump Apple Events — verified).
- **Verified** end-to-end on macOS via `hack/openwith`: launch-file, launch-URL, two-process already-running forward (argv+socket), **AE odoc** (`open -a <bundle> <file>`) and **AE GURL** (`open myapp://…` against a Launch-Services-registered bundle) all deliver. Classifier unit-tested on every build; delivery tests gated to `-tags ci` (need the test driver's inline event queue; glfw needs a real `Run` loop). **Phase 1 does not** cover mobile (Android intents / iOS `openURL` — follow-up) or the `cmd/bellui` CLI packaging metadata (Info.plist `CFBundleDocumentTypes`/`URLTypes`, AndroidManifest intent filters, `.desktop` MimeType, Windows registry) that makes the OS *route* events to the app — **the API is inert without it** (#155).

### Clipboard Flavors (pre-rebrand tracker #513, Phase 1)
The clipboard carries images, file lists and HTML beyond the text-only `bellui.Clipboard`. Three **optional capability interfaces** (clipboard.go) are asserted from `bellui.CurrentApp().Clipboard()` — on platforms/flavors without support the assertion fails (never a silent no-op):
- `bellui.ImageClipboard` — `Image() (image.Image, bool)` / `SetImage(image.Image)`
- `bellui.FileClipboard` — `Files() []bellui.URI` / `SetFiles([]bellui.URI)` (file-manager copy/paste interop; only `file`-scheme URIs are written, others skipped with a logged error)
- `bellui.HTMLClipboard` — `HTML() (string, bool)` / `SetHTML(html, plainFallback string)` — **always writes the plain flavor alongside** in one transaction (`Content()` reports the fallback afterwards)
- `bellui.MultiFlavorClipboard` (pre-rebrand tracker #583) — `SetFlavors(ClipboardContent)` writes **several flavors in one transaction** (e.g. a rendered chart as image + HTML data table + text fallback), which the single-flavor setters cannot express (each replaces the whole clipboard). `bellui.ClipboardContent{Text, HTML, Image, Files}`: zero-valued fields are omitted, a wholly zero value clears, `Content()` reports `Text` afterwards. Sugar: `bellui.SetClipboardFlavors(content) bool`. Per platform: Linux maps 1:1 onto the glfw fork's transaction-native `SetClipboardData`; macOS writes one `NSPasteboardItem` carrying text/HTML/PNG+TIFF plus one file-URL item per file via a single `writeObjects:` (a >1-item write sleeps 50 ms afterwards — item delivery to the pasteboard server is async and items beyond the first are lost if the process exits immediately; the SetFiles readback trick does not cover this); Windows one `Empty`+multiple-`SetClipboardData` transaction (`belluiWinClipboardSetFlavors`, composing the extracted `putClipboardText`/`buildDropFiles` helpers); wasm one ClipboardItem with text/html/png MIMEs — `Files` is skipped there with a logged error (no portable browser flavor, consistent with wasm not implementing `FileClipboard`); mobile (pre-rebrand tracker #1142) iOS = one pasteboard item published as an **`NSItemProvider`** with explicit fidelity order `public.html` → `public.png` → `public.utf8-plain-text` (a bare `UIPasteboard.items` dictionary carrying all three UTIs pastes **nothing** into Notes — any two paste fine; device-bisected pre-rebrand tracker #1144 — and provider-promised data is materialized by the pasteboard daemon, surviving writer exit), Android = one `ClipData.Item(text, htmlText, null, imageUri)` (a single item natively carries all three; PNG staged through BelluiFileProvider like pre-rebrand tracker #580, MIMEs listed in the `ClipDescription`; Java `doSetClipboardFlavors` — dex regen required) — `Files` skipped with a logged error on both. Test driver stores all flavors simultaneously (the one non-exclusive write). Live-verified macOS (pbpaste/Swift readers), Linux X11 (xclip: 5 MIME targets on one selection), Windows (in-session round-trip). Probe: `clipboardprobe set-multi [file…]`.

Package-level sugar follows the `AnnounceToScreenReader` fallback pattern: `bellui.ClipboardImage/SetClipboardImage/ClipboardFiles/SetClipboardFiles/ClipboardHTML/SetClipboardHTML`; **setters return `bool`** = "clipboard supported this flavor". Getters return `(zero, false)` for both "empty" and "unsupported"; capability absence is signalled only by the assertion / sugar bool.

**Platform matrix**: macOS + Windows + **Linux desktop (X11 + Wayland, Phase 2)** = all three flavors; **wasm = image + HTML only** (no portable browser file-list flavor; best-effort behind clipboard permission + transient user activation — reads start synchronously in the post-gesture turn, rejection degrades to `(zero, false)`); test driver = all three in-memory (exclusive-flavor semantics); mobile = image paste (pre-rebrand tracker #580) plus multi-flavor `SetFlavors` (pre-rebrand tracker #1142) — `HTMLClipboard`/`FileClipboard` stay unimplemented there (no HTML getter, no file flavor).

Implementation: `internal/driver/glfw/clipboard_flavors_{darwin,windows,linux,wasm}.go` add methods to the shared `clipboard` struct per-platform (upstream GLFW is string-only, so darwin uses an ObjC NSPasteboard bridge — PNG+TIFF, `writeObjects:` promises force-flushed by reading each item back — and windows a plain-C Win32 bridge — registered "PNG"+CF_DIB, CF_HDROP, "HTML Format"+CF_UNICODETEXT, retry only on failed `OpenClipboard`). **Linux rides on the forked GLFW's generic MIME clipboard API** (C: `glfwSetClipboardData`/`glfwGetClipboardData`/`glfwGetClipboardTargets`; Go: `glfw.SetClipboardData([]ClipboardFlavor)` etc.): the C layer owns the X11 CLIPBOARD selection (dynamic TARGETS, MULTIPLE, outgoing **INCR** transfers for large payloads, both directions) and the Wayland `wl_data_source`/`wl_data_offer` MIME negotiation (offers record the full MIME list; image-only selections are no longer dropped on arrival), dispatched at runtime per platform — compatible with the pre-rebrand tracker #542 runtime-selection plan. Linux flavor MIMEs: `image/png`; `text/html` + `text/plain;charset=utf-8` companion (UTF-16 BOM guard on read); files = `text/uri-list` **and** `x-special/gnome-copied-files` ("copy" op) for GNOME/KDE file-manager interop — both written, both read (the gnome decode rejects payloads whose first line isn't `copy`/`cut` because xclip serves its data for *any* requested target). **Wayland platform limitation**: selection read/write needs keyboard focus (`set_selection` needs a serial from a real input event) — writes from an unfocused window are refused by the compositor. Native calls run via `runOnClipboardThread` (inline on the main goroutine — queueing with wait from the running main loop would self-deadlock). The payload codecs (CF_HTML header block, DIB encode/decode incl. V5/bitfields, text/uri-list + gnome-copied-files in `urilist.go`) are **pure Go in `internal/clipboard`**, unit-tested on every CI leg. Live-verify harness: `hack/clipboardprobe` (CLI ops on desktop; **`--run` managed mode for Linux** — clipboard ops need the running GLFW loop and set-ops must stay alive serving the selection; button UI for wasm). Headless Wayland verify recipe: headless sway + `wtype -k Escape` (instantiates a virtual keyboard on the seat) + `swaymsg '[title=…]' focus`.

### Rich Notifications — Click Activation + Action Buttons + Icon (pre-rebrand tracker #516, Phase 1)
`bellui.NotifierWithOptionsApp` — an **opt-in** optional interface (asserted from the `App`, like `NotifierApp`/`BadgeApp`) for notifications richer than the fire-and-forget `{Title, Content}` `bellui.Notification`. `SendNotificationWithOptions(*bellui.NotificationOptions)` where `NotificationOptions{Title, Content string; Icon bellui.Resource; OnTapped func(); Actions []NotificationAction}` and `NotificationAction{Label string; Callback func()}`. The plain `SendNotification` API is untouched.
- **Free function** `bellui.SendNotificationWithOptions(n) bool` mirrors `bellui.SendNotification`: it asserts the interface and returns whether the rich form was delivered; an app that only implements plain `NotifierApp` **degrades to a title+content notification** (callbacks/actions dropped, never the whole notification). The concrete `belluiApp` implements the rich method on **every** platform, so degradation happens *inside* the platform method where a capability is missing — the "never lose the feature" guarantee.
- **Callbacks are session-scoped and delivered on the main goroutine**: `OnTapped` (body click, the #1 ask) and each action `Callback` fire only while the sending app is still running (activation of a *terminated* app is out of scope — that is pre-rebrand tracker #510 open-with launch-activation territory). Shared plumbing in `app/notification.go`: `registerNotifyCallbacks(opts) → token` (0 when nothing to track), `fireNotifyTapped`/`fireNotifyAction`/`forgetNotify`, all hopping onto the main goroutine via the pre-rebrand tracker #510 `queueOnMain` (`go bellui.Do`) seam; a per-notification temp icon is written by `writeTempNotificationIcon`.
- **Linux/BSD (full)** — `app/app_notification_xdg.go` uses the raw `org.freedesktop.Notifications` D-Bus interface (the portal wrapper has no actions channel, so **Flatpak degrades** to plain). The `actions` array is `["default", "", "bellui-action-0", <label>, …]` — `default` is the body-click, each button an indexed key; a one-time `AddMatchSignal` + `conn.Signal(ch)` goroutine routes `ActionInvoked`→`fireNotify*` and `NotificationClosed`→cleanup (removes the temp icon), keyed by the native notification id returned from `Notify`. **Live-verified end-to-end on GNOME/Wayland**: real `Notify` with the actions array + per-notification icon reaches gnome-shell; emitting `ActionInvoked default`/`bellui-action-0`/`bellui-action-1` + `NotificationClosed` on the session bus fires BODY CLICK / REPLY / LATER callbacks on the main goroutine and removes the temp icon.
- **macOS/iOS (full)** — `app/app_darwin.{go,m}` migrates the rich path to a `UNUserNotificationCenter` **delegate** (`BelluiUNDelegate`): actions become a per-notification `UNNotificationCategory` (identifier `bellui-cat-<token>`, actions `bellui-action-<i>`), the token rides in `content.userInfo`, the icon is a `UNNotificationAttachment`, and `didReceiveNotificationResponse` maps the action id → `//export notifyCallbackDarwin(token, idx)` (idx −1 = body click, ≥0 = action, other = cleanup-only) which fires + forgets. `willPresentNotification` shows banners while foreground. **Requires a bundled app with a valid identifier** — an unbundled/`go run` binary or a bundle whose linker signature carries the wrong identifier can't get notification authorization, so it degrades to the osascript path (the `bellui package` bundle is fine; ad-hoc `codesign -s -` with the real bundle id makes the OS permission prompt appear). Verified live on macOS to the point of the OS permission prompt + `rich=true` send path; the final banner-click callback is interactive-only (the private UN delegate has no injection point like Linux's bus — the shared registry + main-goroutine dispatch it feeds is fully proven by the Linux run).
- **Degraded (documented follow-ups)** — Windows (pre-rebrand tracker #722: needs AUMID + WinRT toast activator; the PowerShell sender has no callback channel), Android (pre-rebrand tracker #723: PendingIntent), wasm actions (pre-rebrand tracker #724: Service Worker; **wasm OnTapped + icon already work** via the `Notification` `onclick`). All degrade to a plain notification; the test-driver app records both the rich options and the reduced plain form.
- Live-verify harness: `hack/notifyprobe` (`-auto` scripted mode). Unit tests: `app/notification_test.go` (registry bookkeeping), `app/app_notification_xdg_test.go` (`parseNotifyActionKey`), `test/notification_test.go` (free-function routing).


### Android Canvas Scale — densityDpi Arithmetic (#272)
The mobile driver derives the Android canvas scale as `densityDpi/160` (`androidScaleForDPI`, `internal/driver/mobile/device.go`), the same arithmetic as `DisplayMetrics.density` — replacing a bucket lookup that rounded off-bucket densities to the nearest of 1/1.5/2/3/4. Off-bucket configurations are common real hardware (the OPD2403 bench reports 356 → scale 2.225, not 2.0; Pixels commonly report 420 → 2.625), and the bucket rounding made everything derived from dp — the #254/#263 48dp touch-target floors, text sizes — up to ~12% off in physical units. The mainstream buckets produce exactly the old scales (160→1, 240→1.5, 320→2, 480→3, 640→4), so phones and tablets configured at a quantized density are untouched — **tvdpi (213) is the one exception**: the old ladder rounded it up to 1.5, the platform's own density is 213/160 = 1.33125, so an Android TV panel configured at tvdpi renders ~11% smaller than before. That is the intended value, and it is the one regression report to expect from this change. Two deliberate edges: at or below mdpi the scale clamps to 1 (no shipping ldpi hardware; keeps the pre-first-size-event dpi-0 state usable) — a deviation from DisplayMetrics; and `windowConfigRead` (`app/android.go`) treats any positive density below `ACONFIGURATION_DENSITY_ANY` as real (no more "unknown density" log), with the ANY/NONE sentinels falling back to mdpi — ANY previously fell through as a 65534dpi screen. iOS keeps its bucket mapping, and the arithmetic must **not** be carried over there: `currentDPI` on iOS is a physical ppi (`app/darwin_ios.go` `setScreen`: 163 for iPhone/iPad mini, 132 for other iPads, times the UIKit scale), not an Android-style density, so `dpi/160` would read a 2x iPhone as 2.04 and a 2x iPad as 1.65 — the lookup is right precisely because UIKit reports exact 1x/2x/3x classes.
- Live-verify harness: `hack/deviceinfoprobe` (auto-reports 2s after launch and on a button; logcat tag `Bellui`, `grep deviceinfo`) — also the #271 raw-locale capture. Verified on the pixel143 AVD (density 420 → scale 2.625, 411pt wide = the Pixel 7's canonical 411dp). Unit tests: `internal/driver/mobile/device_test.go` (`TestAndroidScaleForDPI`, incl. the tvdpi and clamp edges), `internal/driver/mobile/app/density_test.go` (`TestAndroidDPIForDensity` — the density→dpi decision, kept in the cgo-free `app/density.go` because no CI leg compiles `app/android.go`).

### File Watching — forked fsnotify (#68)
File watching (`storage/repository.WatchableRepository` via `internal/repository`, and the app-settings watcher in `app/settings_desktop.go`) runs on **`github.com/belluikit/fsnotify`**, a fork of fsnotify with the module path rewritten — started from v1.9.0, since synced by merging upstream `main` (at v1.10.2: upstream `20b1e15`, v1.10.1 plus 8 commits) — imports swapped at the call site, **no `replace` directive**, exactly like `belluikit/glfw` / `belluikit/glfw-js` / `belluikit/systray`. Everything outside `backend_windows.go` is upstream and untouched; see the fork's `FORK.md`.

Two defects in the Windows `ReadDirectoryChangesW` backend, **both still present on upstream `main`** (checked at v1.10.1), and causally linked:
- **Double `CloseHandle` on a torn-down watch — a process-wide Go runtime fatal.** `readEvents` re-armed a watch unconditionally at the end of its event loop, but the watch is recovered from the completion packet's `OVERLAPPED` pointer and that packet may predate a `remWatch` that already closed its handle and dropped it from `w.watches`. The re-arm closed the same handle a second time. Windows reissues a closed handle's numeric value to the next caller, and in a Go program the most frequent caller is **the runtime itself** (`CreateEvent` in `semacreate`, once per new M) — so the stray close destroys a handle the runtime believes it owns, and the next `WaitForSingleObject`/`SetEvent`/netpoll on it dies with `ERROR_INVALID_HANDLE`. That is the `runtime.semawakeup` / `runtime.semasleep wait_failed` / `netpoll failed` family (all `errno=6`) that made `windows_arm64_tests` the largest source of red CI, with a stack pointing nowhere near fsnotify. **Fix:** drop completion packets whose watch is no longer registered.
- **`sendError` swallowed `Close`'s handshake token.** `w.done` (cap 1) carries the reply channel that is `Close`'s only handshake with the reader; `sendEvent` puts it back, `sendError` dropped it — so an error reported while a `Close` was in flight left `Close` blocked forever on a reply that could never come, with the reader parked in `GetQueuedCompletionStatus` having already consumed the wakeup. This is the hang `closeWatcher` still carries a bounded 5s backstop for (the old pre-rebrand tracker #963 note). The double close is what *made* `CancelIo` fail, which is what called `sendError` — so the first defect was a frequent cause of the second. **Fix:** put the token back.

**The original theory in #68 — handle *exhaustion* from `closeWatcher`'s leak — was wrong, and the errno is why**: `ERROR_INVALID_HANDLE` on a handle the runtime already owns is a *stray close*, not a failure to allocate. Measured on the windows/arm64 runner: the process handle count never drifted anywhere near exhaustion, while an instrumented build counted **2404 double closes per 150 rounds** of Add/Remove churn (0 after the fix), and bellui's own watch tests reproduced the runtime fatal within 3 iterations before the fix and not once in 160 runs after.

**Verify:** `go run ./hack/winwatchprobe -rounds 200` on a Windows box reports the two numbers that track this — bail-out rate (a `Destroy` taking ≥5s means `closeWatcher` gave up and leaked the reader; was 4 per 200 rounds, now 0) and process handle drift (was creeping, now flat). Retire the fork when the fixes land upstream.


### iOS Packaging — the `ios/` Directory (#672)

`bellui package -os ios` takes what `manifest.pxf` cannot express from files
next to the app's main package, the way `android/*.java` works on Android:
`ios/Info.plist` and `ios/Entitlements.plist` (plist dict fragments) and
`ios/Frameworks/` (`.xcframework` / `.framework`). The user-facing rules are in
`cmd/bellui/README.md`; the design points:

- **Files, not manifest fields** (owner decision, 2026-10-22). A plist fragment
  holds any plist type with no typed-value encoding in PXF or the manifest
  proto. The cost: a static file cannot vary per build, so dev/release-split
  entitlements (`aps-environment`) are not expressible.
- **One source of truth per key.** A fragment key the packager owns or derives
  from the manifest is an error, never a silent override. Generated defaults
  (orientations, `UIRequiresFullScreen`, …) are the fragment's to replace.
  The merge is a real plist tree (`internal/mobile/plist.go`), so key order is
  deterministic.
- **Frameworks link through cgo, embed through Xcode.** The Go binary is built
  outside Xcode and copied in as a resource, so the slice for each GOARCH is
  added to that architecture's `CGO_CFLAGS`/`CGO_LDFLAGS` (plus
  `-rpath @executable_path/Frameworks` when one is dynamic). Dynamic
  frameworks are copied into the Xcode project and an Embed Frameworks phase
  with `CodeSignOnCopy` signs them with the app's identity; copying into the
  .app after xcodebuild would break the seal. `bellui release` re-signs each
  with the release certificate before the app.
- **Swift is not compiled** by the packager; it ships as an xcframework.
- Verified with `hack/iosframeworkprobe` (bundle inspection; see its doc
  comment for the device run).

### Android library dependencies in `bellui package` (#672)

`<appdir>/android/libs/*.jar|*.aar` are packaged without Gradle; the user-facing
description is in `cmd/bellui/README.md`, the code in
`cmd/bellui/internal/mobile/android_libs.go`.

- **File convention, not manifest.pxf fields** (owner decision, 2026-10-22): the
  same envelope as `android/*.java` and a custom `AndroidManifest.xml`. A static
  directory cannot vary per Development/Release build.
- **AARs switch resources to aapt2.** Library res needs a real link and R
  classes, which binres cannot do. Libraries are `-R` overlays in file-name
  order and the app's own resources come last, so the app wins a name clash.
  `--extra-packages` generates an R class for every library package with
  resources, or with a non-empty `R.txt` (an AAR built with transitive R reads
  its dependencies' resources through its own R). The R sources are compiled
  and dexed with the app, which is why linking now runs before dexing.
- **No AAR, no change.** Without an AAR the binres path is untouched; a test
  pins the manifest byte-identical with and without a jar.
- **Simplified manifest merge**: permissions, features, queries and
  `<application>` children, deduplicated by `android:name` with the app first.
  A component two libraries share has its children merged (androidx.startup's
  `InitializationProvider` carries one `<meta-data>` per library), and
  relative class names are qualified with the declaring library's package, as
  the Gradle merger does.
  No `tools:` directives, no `<application>` attribute merge, no placeholder
  other than `${applicationId}`. Upgrade path if a library needs more: the
  app's own `AndroidManifest.xml`.
- **Missing ABI is an error**: an AAR with `jni/` for some ABIs but not a built
  one would install and then fail `System.loadLibrary` on exactly those devices.
- **One platform for javac, d8 and aapt2**: app Java is compiled and dexed
  against `binres.LatestAPIResourcesPath`, the `android.jar` aapt2 links
  against, so the R classes and the code agree on one API level.
- **Multidex in the AAB**: d8 may write `classes2.dex`…; the bundle's base
  module takes every `classes*.dex` into `dex/`.
- **Build-tools selection**: `util.AndroidBuildToolsPath` used to take the
  lexically first (oldest) build-tools; d8 2.1.7 from 30.0.3 crashed on the
  android-35 `android.jar` given as `--lib`. It now takes the newest.
- **Verify** with `hack/androidlibprobe` (androidx.core 1.3.2 closure; expects
  `androidlibprobe ok color=#ff9e9e9e overflow=999+ arrayset=2`).
